## 0. 先决问题：先看许可，再谈二次开发

「二次开发」能不能成立，取决于基座许可证。这条不定，优点的收集方式就不同。

| 项目 | 语言/框架 | 许可证 | 能否合法二开并发布 |
|---|---|---|---|
| HMCL | Java + JavaFX | GPL-3.0 | 可以。但衍生版必须同样 GPL-3.0 开源、保留版权声明、提供完整源码 |
| Prism Launcher | C++ + Qt | GPL-3.0 | 同上（GPL-3.0） |
| ATLauncher | Java | GPL-3.0 | 同上 |
| FCL / PojavLauncher | Java + Android | GPL-3.0 | 同上（仅安卓） |
| XMCL | TypeScript + Electron + Vue | MIT | 可以，闭源商用也允许（保留版权声明即可） |
| Helios Launcher | JS + Electron | MIT | 同上 |
| PCL2 / PCL CE | VB.NET + WPF | PCL 分发有限许可（非 OSI） | 不可以自由二开再发布；只能借鉴功能与交互思路，不能搬代码 |
| BakaXL / LauncherX / MCLaunch | 闭源 | 专有 | 只能借鉴思路 |

**结论：**

- 想「合法二开、立刻出成果」→ 只能在 HMCL / Prism / XMCL 里选基座；选 GPL 系就必须全程开源，不能闭源商业化。
- 想「自己掌控、以后能商业化、代码干净」→ 从零写，把各家当产品参考而非代码来源。工作量最大，产权最清晰。
- 折中：自己写外壳与核心，只把 MIT/Apache 许可的库拿来做组件（下载器、压缩包解析、Java 探测、认证流程等）。

> 未验证：以上许可判定来自公开仓库惯例认知，正式选型前应逐项打开仓库 LICENSE 原文复核一次。

## 3. 可借鉴的具体设计（不涉代码）

1. **PCL 的分段启动进度 + 人话报错**：把启动拆成可解释阶段，失败时给归因和下一步动作，而不是抛堆栈。
2. **PCL 的镜像测速择优**：多源并发探测，按实测速度选源，失败自动降级。
3. **HMCL 的 Java 全生命周期**：探测 → 按版本推荐 → 缺就下载 → 校验 → 失败回退手动指定。
4. **Prism 的实例即目录**：一个实例 = 一个自包含目录，导入导出就是复制目录，避免全局 .minecraft 被写脏。
5. **Prism 的组件页**：Mod/资源包/光影/世界/服务器列表统一成「组件」，统一启用/禁用/更新语义。
6. **XMCL 的 P2P 联机**：零配置建房，是国内用户真正痛点。
7. **XMCL 的插件化**：核心小、功能外挂，便于社区贡献。
8. **BakaXL 的动效与「不像工具」的观感**：降低新手门槛（但要克制，动效不能拖慢响应）。
9. **Helios 的「私服即产品」**：把某个服务器打包成专属启动器，是一类真实需求。

## 4. 反面清单（别人踩过的坑，别重复）

- 列表不虚拟化 → 上千个 Mod 卡死（JavaFX/Qt/WPF 都会）。
- 全局 .minecraft 直接写 → 多版本互相污染，卸载版本带走存档。
- 下载全串行 → 大整合包装一小时。
- 直接删文件做「清理」→ 用户存档丢失；应走回收站/备份。
- 把「启动成功」当「游戏能玩」→ 缺少进入世界后的验证。
- 自更新无签名/无回滚 → 更新失败变砖。
- 配置存注册表/系统目录 → 换机即丢；应可导出。
- Electron 起步快但体积 100MB+，国内下载分发成本高。

## 6. 需要用户先拍板的三件事（决定第二步怎么评）

1. **基座路线**：A 从零写（产权最干净）／B 基于 HMCL 或 Prism 二开（快，但整体 GPL 开源）／C 自写外壳 + 宽松许可组件（折中）。
2. **平台范围**：只 Windows，还是一开始就三平台？（直接影响 UI 框架：WPF/Avalonia/Qt/Electron）
3. **是否要能商业化/闭源**：决定 GPL 系能不能碰。

> 这三条不定，「评估优先级」会得出互相矛盾的结论（例如既选 HMCL 又要求闭源）。
