# 鸭嘴兽启动器 · 第二步：优先级评估与路线

> 输入：从零写、开源、三端、Android 优先、Win 次之；手机端「真的玩 Java 版」与「管理端」都要；不急，求最好、不卡、好用。
> 时间：2026-11-08

---

## 1. 分层架构（先把边界画死）

```
platypus/
  core/          纯 Kotlin，无 UI、无平台依赖（可单元测试）
    download/    多源、测速、并发、续传、校验
    instance/    实例 = 自包含目录；版本清单与文件布局
    auth/        离线 / 微软 / 外置登录
    java/        探测、按版本推荐、下载、校验
    launch/      启动计划 → 进程 → 退出码与日志归因
    content/     Mod / 资源包 / 光影 / 世界的统一「组件」模型
    server/      开服、properties、白名单、RCON
    pack/        整合包安装与导出（mrpack / CurseForge zip）
  ui/            Compose Multiplatform，两端共享设计语言、各自布局策略
  platform/      expect/actual：文件、进程、注册表、通知、沙箱
  runtime-android/  **独立模块**：JRE + LWJGL/OpenGL 移植 + 输入映射
  runtime-desktop/  启动进程管理（相对简单）
```

关键决定：**把「运行 Minecraft」抽成 runtime 接口**。桌面实现是「起一个 java 进程」，Android 实现是「在应用内起 JVM + 图形转译」。上层 core 只认接口，这样两端能共用 80% 的逻辑。

## 2. 功能优先级（价值 × 成本 × 风险）

评分：价值 1–5（越大越重要）、工作量 1–5（越大越费）、风险 1–5（越大越不确定）。

| 功能 | 价值 | 工作量 | 风险 | 结论 |
|---|---|---|---|---|
| 实例隔离与版本管理 | 5 | 2 | 2 | **先做**，地基 |
| 下载器（多源/测速/并发/续传/校验） | 5 | 3 | 2 | **先做**，所有功能都靠它 |
| Java 探测/推荐/下载 | 5 | 2 | 3 | **先做**，桌面端直接可用 |
| 账号（离线/微软/外置） | 4 | 2 | 2 | 先做 |
| 启动链路与失败归因 | 5 | 3 | 3 | 先做 |
| Android 运行端（JRE + 渲染） | 5 | 5 | 5 | **攻坚**，见第 3 节 |
| 整合包安装/导出 | 4 | 3 | 3 | 第二批 |
| 内容管理组件页 | 4 | 3 | 2 | 第二批 |
| 服务端一键开服 | 4 | 3 | 2 | 第二批（上一项目已有经验可迁移） |
| Android 管理端（连 PC、看日志、远程开服） | 4 | 2 | 2 | 可早做，成本低、见效快 |
| P2P 联机 | 5 | 4 | 4 | 第三批，差异化 |
| 自更新（带回滚） | 3 | 2 | 2 | 第三批 |
| CLI / 自动化 | 2 | 3 | 2 | 差异化点缀，不急 |
| 插件 API | 2 | 4 | 3 | 最后再说 |

**排序原则**：先做「所有其他功能都依赖它」的地基（实例、下载、Java、启动），再做「看得见效果」的（组件页、开服），最后做「差异化但有风险」的（联机、运行端）。

但有一个例外，见下节。

## 3. Android 运行端必须先做可行性验证（Spike S1）

理由：它不是「一个功能」，是**平台能力**。它成立与否，决定了「手机优先」是产品主线还是宣传语。如果它不成立，产品定位要立刻改成「手机管理端 + PC 运行端」，架构也随之变化。这个结论越早拿到越好。

预研要回答四个问题（都要有数字，不能是「感觉可以」）：

1. **能跑起来吗**：在目标机型上跑通一个原版客户端（例如 1.20.1 或 1.21.x），进入世界。
2. **跑多快**：进入世界后 10 分钟的平均帧率、帧时间抖动、峰值内存。分档记录：旗舰 / 中端 / 低端。
3. **兼容性**：Forge/NeoForge/Fabric 加载器能否加载；主流光影/资源包能否工作；32 位与 64 位差异。
4. **温度/耗电**：连续 30 分钟的表面温度与掉电速率，判断「能不能真玩」。

做法：先用现成组件搭最小闭环（Pojav 的 JRE 与 GL4ES 路径是最好的参照），**只做测量，不做产品**。产出一份《Android 运行端技术基线报告》，里面全是数字。这一步大约需要 1–2 周，且不需要等 UI 框架定案。

> 提醒：这里参考的是 Pojav 的**公开技术路线**（GPL-3.0）。我们只借鉴「用什么渲染后端、JRE 怎么打」这类事实性知识，代码一行不拷。

## 4. 里程碑

| 里程碑 | 内容 | 验收标准 |
|---|---|---|
| **M0** | 项目骨架、CI、协议、代码规范、core 的接口定义 | 能编译、能跑测试、Empty UI 能起 |
| **M1** | core 地基：实例 + 下载器 + Java + 启动（桌面） | 命令行能装一个版本并启动成功 |
| **M2** | 桌面端可用的 UI（Compose Desktop） | 装版本、登录、启动、报错归因全通 |
| **M3** | Android 管理端 | 手机上能看到 PC 实例、日志、远程开服 |
| **M4** | Android 运行端（依赖 S1 结论） | 手机上进入世界并稳定运行 30 分钟 |
| **M5** | 内容管理 + 整合包 + 服务端 GUI | 一站式可用 |
| **M6** | 联机 / 自更新 / 打磨 | 发布第一个可用版本 |

## 5. 性能预算（「不卡」要变成数字）

| 场景 | 指标 | 目标 |
|---|---|---|
| 桌面冷启动到首屏 | 时间 | ≤ 1.5 s |
| 列表滚动（1000 项 Mod） | 掉帧 | 无可见卡顿，60 fps |
| 下载 100 个文件 | 并发 | ≥ 16 并发，进度刷新 ≤ 100 ms |
| Android 首屏 | 时间 | ≤ 2.5 s（中端机） |
| 内存（桌面空闲） | RSS | ≤ 250 MB |
| 内存（Android 后台管理端） | RSS | ≤ 150 MB |

这些数字进 CI 或至少进每次里程碑验收，避免「后期再优化」变成「永远不优化」。

## 6. 现在就能定的三件事

1. 协议 **Apache-2.0**（若你要防别人闭源拿走，就换 GPL-3.0，但你自己也必须一直开源）。
2. 第三端先按 **Linux** 准备（macOS 的签名/公证会拖慢早期迭代，等产品稳定再加）。
3. **立刻启动 S1 spike**，与 M0/M1 并行——它不依赖任何 UI 决定。

## 7. 下一步建议

先做 M0 + S1 两件事，都是「不需要等」的：

- M0：把仓库骨架、模块边界、许可证、代码规范立起来（半天到一天）。
- S1：Android 跑通并测出数字（一到两周，可与 M0/M1 并行）。
