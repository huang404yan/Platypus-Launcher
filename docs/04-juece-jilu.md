# 决策记录

按时间倒序。每条记录：决定、理由、被放弃的选项。

## 2026-11-10

### D16 实例真隔离：`--gameDir` 指实例目录，libraries/assets 共享

- 决定：**一个实例 = 一个自包含目录**（`<游戏目录>/versions/<id>/`）。启动时 `--gameDir` 经 `InstanceLayouts.of()` 算出，指向实例目录本身；`libraries/` 与 `assets/` 仍从游戏根目录（再上两级）取，共用一份。存档、模组、配置、日志、资源包、光影、截图、崩溃报告全部落在实例目录下。
- 背景（改造前是三方矛盾）：`Instance.kt` 的类注释早就写着「一个实例 = 一个自包含目录」，但 `DesktopGameRuntime.resolveLayout` 把 `--gameDir` 反推回 `<游戏目录>`，于是所有实例共用 `saves/`、`mods/`、`options.txt`；`ModScanner` 的注释甚至明说「所有实例共享」；而 `InstanceDeleter` 又按 `<版本目录>/mods`、`<版本目录>/saves` 统计与搬移存档——三处各说一套，删除器其实已经假设了隔离。
- 为什么不加新字段：唯一真源仍是 `Instance.directory`（就是版本目录）。加 `gameDirOverride` 之类的字段会让「这个实例到底用哪个目录」有两个真源，且要改 `instances.json` 的序列化兼容。
- 为什么不走 `-Dminecraft.gameDir` 或切 cwd：Mojang 的启动参数里 `game_directory` 就是 `--gameDir` 一项，`-Dminecraft.gameDir` 是旧版 Forge 的私有约定，不可靠；切 cwd 会同时影响相对路径的库与日志，副作用更大。
- 旧数据兼容：隔离后 `<游戏目录>/mods` 里隔离前装的模组不再被任何实例看见。`InstanceMods` 会把它扫出来并在模组页提示「共享 mods/ 里还有 N 个模组」，提供「搬进这个实例」——**复制不移动、默认不覆盖同名、源文件不删**。删除用户文件的操作必须由用户自己动手。
- 懒得上溯：`InstanceLayouts.gameRootOf` 只在父目录确实叫 `versions` 时才往上走两级，否则退回目录自身。宁可把 `libraries/` 指到一个空目录、启动时明确报「缺库」，也不要凭空猜一层跑到别人的游戏目录去。
- 放弃：把 libraries/assets 也按实例复制一遍（1.20.1 实测 libraries 64 MB + assets 796 MB，每个实例复制一份是灾难）；把隔离做成开关（两套运行路径，测不完）。

### D17 左下导航维持一级，实例详情做成「钻进一个」而不是第九个入口

- 决定：详情页不进 `Page` 枚举。实例列表里点「详情」切到详情面板，面板顶部「← 返回实例列表」回去；左侧导航仍高亮「实例」。
- 理由：`Page` 是「产品的一级分区」，实例详情是「列表里某一行展开」，不属于同一个层级。把它塞进枚举会让导航多出一个永远不该单独点的项，还会让「当前在哪个分区」这个问题的答案变成两个。
- 与 Q3（左侧两级导航）的关系：Q3 定的两级导航是指「实例 / 下载 / 设置」各自往下带子项（实例→概览/模组/存档，下载→原版/模组/整合包），详情页不是子项，是子项里的第三个层级。S1 改造时详情继续走「钻进一个」，只是从实例列表换成实例子页里进。
- 放弃：详情做成独立窗口（桌面端可以，但安卓没有这个形态，两端就会分叉）；详情做成弹窗（信息量太大，要展示目录树、Java 列表、占用统计）。

## 2026-11-09

### D15 断点续传靠 `.part` + Range，实例页只管「登记」不碰磁盘

- 决定：下载器改成「先写 `<target>.part`，校验通过才转正；`.part` 有内容就发 `Range` 接着下」；实例页拆成独立文件并加「新建 / 改内存 / 登记 / 移除登记」，**但移除登记不删任何版本文件**。
- 理由（续传）：断网一次就把已下的几百 MB 全清掉，这不是「不够快」而是「不可用」。1.20.1 全量实测 651,738,281 B，重下一次的代价用户能直接感受到。改造成本只有一条请求头加一套保留/删除的判定，收益是任何中断都变成可恢复。
- 续传的两个硬性细节，写进代码注释而不是只写在文档里：① 必须发 `Accept-Encoding: identity`，否则 gzip 会让 `Content-Range` 的偏移对不上；② **只有「内容已不可信」才删 `.part`**（写多了、sha1 不符、起点对不上），网络异常与提前 EOF 一律保留——这条判定反过来写就等于没做续传。
- 理由（实例页）：实例页要能建实例，否则「本地已经有一份游戏」的人没有入口，只能重新下一次。判断「本地已有」的判据是 `VersionResolver.load()` 成功**且 client jar 非空**——只判 json 存在会把「下了一半」当成「已下好」。
- 「移除登记」只从 `instances.json` 里去掉一条，**不删磁盘**：登记表是启动器自己的账，磁盘是用户的文件。实现成删目录的话，用户点一次「移除」就永久丢一份几百 MB 的游戏，且不可撤销。
- 放弃：只在失败重试时续传（用户手动取消的那次照样白下）；用 `HEAD` 先问长度再决定（多一次往返，且 `Content-Length` 与 `item.size` 已知时没有额外信息）；把「本地认养」直接写进 Composable（无法单测，也无法被无头冒烟复用）。

### D14 启动器设置单独存一份 JSON，不跟进实例索引

- 决定：离线用户名、默认游戏目录、新实例默认内存三项进 `<gameRoot>/platypus/settings.json`（无 gameRoot 时落 `<user.home>/.platypus/settings.json`），走 `SettingsRepository` 接口；实例自己的内存仍存在 `instances.json` 里，两处互不覆盖。
- 理由：改造前界面**已经能填离线用户名**，但不落盘，关掉窗口就回 `Dev`；默认目录每个页面各自记、互不知情；一键装出来的实例内存恒 2048。这三件都直接卡在「双击能不能玩」上（D12 的硬标准），属于本轮必须补的缺口。
- 设置文件**刻意不跟着用户当前选中的目录漂移**：设置里记的就是那个目录，文件若也跟着走，换一次目录就看不到上次的选择。
- 实例内存与默认内存分工：设置页的 `defaultMemoryMb` 只决定「新建实例的初值」，具体实例改内存仍在启动页，落 `instances.json`。避免同一份数据两个真源。
- 放弃：把设置塞进 `instances.json`（索引文件要能重建、要能只靠扫描恢复，混进用户偏好就毁了这条路）；用 `java.util.prefs` 或注册表（不可见、不可备份、跨用户不通用）。

### D13 开发优先级 Win > Android，发布两端同时

- 决定：**Windows 端为唯一活动开发线**，Android 端暂停；待 Win 一键装闭环稳定后再回到 Android。对外发版时两端同一版本号**同时出包**，不允许只发一端。
- 理由：用户原话「多线容易抢工具导致进度缓慢，优先级 win>a，优先 win 端开发后续开发 a 端；发布同时发」。两条线并行会争抢 gradle daemon、文件锁与网络带宽，实测同一时段内两条线的构建互相阻塞。
- 放弃：双线并行（已被实测证明拖慢）；先发 Win 再补 Android（会造成"两端不同步"的用户观感，与 D10 双号段规则冲突）。

### D12 以 PCL 自编版的功能集为「小目标」，但按「少了它还能不能玩」分档

- 决定：把上一项目（PCL-拾光启动器自编版）的功能表当作**功能参照系**，不当界面或实现参照系；并按一句硬标准分两档——**去掉这一步，用户还能不能双击把游戏玩起来**。不能的进本轮，能的排以后。
- 本轮（能玩起来的充分链条）：选版本 → 下载（带进度）→ 缺 Java 自动补齐 → 登记成实例（内存可改）→ 一键启动进主菜单。
- 以后（本轮明确不做）：正版 / 离线 / Authlib 三方登录、陶瓦联机、服务器安装与启动、控制台、RCON、server.properties 表单、OP 管理、Forge/NeoForge 内存改写、主题配色、自动更新、帮助文档。
- 理由：用户原话「参考上次 pcl 自编版为小目标开发，只向功能」——要的是能力对齐，不是复刻。若把登录、联机、服务器一起铺开，闭环会拖成半成品，反而验证不了「双击就能玩」这件事。
- 对 Android 线额外约束：PCL 功能表的前提是 S1 spike 成立。若 S1 证明应用内跑 Java 版在该机型不成立，这份表对 Android 只是**上限参考**，报告须写明哪几步做不到、卡在哪、需要换机型还是换渲染方案，不接受「理论上可以」。
- 放弃：一次性对齐 PCL 全部功能（范围失控，且当前连实例化都没有）；只做界面不做闭环（与上一轮「能编译 ≠ 能用」的教训冲突）。

### D10 单一公开测试通道：鸭嘴兽·孵化版（Platypus Preview）

- 决定：只保留两条线——正式版「鸭嘴兽启动器」与唯一公开测试版「鸭嘴兽·孵化版」。不另起内测/公测/灰度之类渠道名，测试版只靠 `preview.N` 进位。
- 理由：渠道越多，版本矩阵与用户反馈越混乱；「孵化」既对应鸭嘴兽的卵生设定，也点明这是未定型的预览线。
- 标识：Android applicationId 两条线各用独立包名（正式版 `.launcher`、孵化版 `.launcher.preview`）——理由见下方 D11；桌面命令行 `platypus-launcher` / `platypus-launcher-preview`；Linux 桌面文件 `platypus.desktop` / `platypus-preview.desktop`；安装包命名如 `Platypus-Launcher-0.8.0-preview.3-win-x64.msi`。
- 版本号：正式版从 1.0.0 起按语义化进位；孵化版为 `0.x-preview.N`。
- 当前落点：仓库现处 0.8.0-preview.4（孵化线），正式版 1.0.0 待启动链路跑通后再立。

### D11 Android 两条线各用独立包名（2026-11-08）

- 决定：正式版 `io.github.huang404yan.platypus.launcher`，孵化版 `io.github.huang404yan.platypus.launcher.preview`（品牌表最初写法，最终确认采用）。
- 理由：孵化版是「可以随便炸」的实验线，正式版是「装了就指望它稳定」的发布线。两个包名意味着同一台设备可同时装、互不影响，测试出问题不会污染正式版数据目录；也符合「孵化版不占正式版版本号」的双号段规则。
- 代价：孵化版的改动迁到正式线时要换包名重出一次（不能覆盖安装），且孵化版的用户数据不会自动带过去。在尚未有真实用户的阶段，这不构成负担。
- 已落地：`androidApp/build.gradle.kts` 里 namespace 与 applicationId 都是 `.launcher.preview`，源码在 `androidApp/src/main/kotlin/io/github/huang404yan/platypus/launcher/preview/MainActivity.kt`；构建脚本加了 `check()`，版本号不含 `-preview` 却仍用孵化包名时直接失败，防止发错线。
- 放弃：两条线共用一个包名——两版不能并存，且正式版与孵化版共用同一份用户数据，实验性改动会动到正式环境。

### D1 从零写，不 fork 任何现有启动器

- 决定：路线 A，自建仓库，不基于 HMCL / Prism / XMCL 二开。
- 理由：PCL 的版权问题只是导火索，根本原因是「集各家优点」没法靠改别人的架构实现；GPL 系 fork 会强制整体开源并继承对方的架构债。
- 放弃：fork HMCL（快但架构绑定）、fork XMCL（MIT 最自由，但 Electron 体积与「不臃肿」冲突）。

### D2 Kotlin + Compose Multiplatform

- 决定：核心纯 Kotlin，UI 用 Compose MP，Android 与桌面共享。
- 理由：Android 本身是 JVM；手机要跑 Java 版 MC 就必须有 JVM，Kotlin 与之同构，避免两套技术栈；MC 周边库在 JVM 生态最全。
- 放弃：C# + Avalonia（桌面最优但 Android 等于重开）、Rust + Tauri（体积最优但开发慢 2–3 倍）、Flutter（与 JVM 交互成本高）。
- 代价：桌面端冷启动与原生观感弱于 WPF，需要靠懒加载与 CDS 补。

### D3 许可证 Apache-2.0

- 决定：Apache-2.0，允许商业化，允许他人闭源二次使用。
- 理由：用户明确「纯开源，最多更新慢」。
- 放弃：GPL-3.0（能防别人闭源拿走，但也锁死自己）。

### D4 三端，Android 优先

- 决定：Android 与 Windows 同时推进，Linux 作为第三端准备。
- 设备基线：Windows 本机；Android 骁龙 870 / 8 GB / 256 GB；Linux 老机器（不保证可运行）。
- 影响：所有性能预算以中端 Android（870）为下限。

### D5 GameRuntime 抽象

- 决定：把「运行 Minecraft」抽成接口，桌面与 Android 各自实现。
- 理由：两端运行方式差异极大（子进程 vs 应用内 JVM + 图形转译），但上层逻辑（实例、下载、账号、启动参数）可以共享。
- 影响：core 不得直接依赖 `Process` 或 Android API。

### D6 性能预算写进验收

| 场景 | 目标 |
|---|---|
| 桌面冷启动到首屏 | ≤ 1.5 s |
| 1000 项列表滚动 | 60 fps，无可见卡顿 |
| 下载并发 | ≥ 16 |
| Android 首屏（870） | ≤ 2.5 s |
| 桌面空闲内存 | ≤ 250 MB |
| Android 管理端内存 | ≤ 150 MB |
